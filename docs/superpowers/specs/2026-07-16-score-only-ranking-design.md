# 점수 전용 장소 평가·정렬 설계

**작성일:** 2026-07-16

**상태:** 검토 요청

**대상:** 사진·리뷰 분석, 장소 점수 계산, 실행 이벤트, JSON 리포트, 웹 리포트 화면

**기준 문서:**

- `docs/superpowers/specs/2026-07-13-analysis-nodes-design.md`
- `docs/superpowers/specs/2026-07-14-json-report-storage-design.md`
- `docs/superpowers/specs/2026-07-15-frontend-web-app-design.md`
- `docs/superpowers/specs/2026-07-15-observability-event-timeline-design.md`

## 1. 배경과 문제

현재 사진·리뷰 분석은 각각 `matched` 불리언을 생성한다. 활성 분석 중 하나라도
`matched=false`이면 장소 결과가 `not_matched`가 되고, 이미 계산된 개별 점수가 있어도
최종 점수를 만들지 않는다. 웹 리포트도 해당 장소를 점수 목록에서 제외하고 별도의
`기준 미충족` 영역에 표시한다.

이 구조는 다음 문제를 만든다.

- 점수가 충분히 높아도 LLM의 이진 판정 하나로 순위에서 제외될 수 있음
- `충족/미충족` 경계가 프롬프트 해석에 의존하여 결과가 불안정함
- 사용자는 후보 전체의 상대적 우열을 확인할 수 없음
- 점수와 이진 판정이 서로 다른 결론을 보여 설명하기 어려움

## 2. 목표

- 정상적으로 분석된 모든 장소에 최종 점수를 부여함
- 최종 점수 내림차순으로 후보 전체를 표시함
- 사진·리뷰 점수와 근거는 유지함
- `matched`, `not_matched`, `mismatchReason` 계약과 UI를 제거함
- 수집·분석 자체가 실패한 장소만 별도 실패 결과로 구분함
- 신규 계약에 맞지 않는 기존 JSON 리포트는 삭제하고 마이그레이션하지 않음

## 3. 비목표

- 최소 추천 점수 또는 통과 임계값 도입
- 상위 N개만 노출하는 필터 도입
- 점수 전용/기준 판정 모드 전환 기능
- 기존 리포트 스키마의 하위 호환이나 자동 변환
- 현재 사진·리뷰 가중치 입력 방식 변경
- LLM 모델, 장소 수집 방식, 리포트 저장 위치 변경

## 4. 확정 결정

### 4.1 이진 판정 제거

사진·리뷰 분석 결과는 점수와 근거만 반환한다.

```text
PhotoAnalysis
  photoScore: 0..10 정수
  reason: 비어 있지 않은 문자열

ReviewAnalysis
  reviewScore: 0..10 정수
  reason: 비어 있지 않은 문자열
```

`matched`는 모델, LLM 구조화 출력, 프롬프트, 그래프 상태, 실행 이벤트, 서버 로그,
프런트 계약에서 제거한다. 분석 기준 문장은 통과 조건이 아니라 0~10점 평가 축으로만
사용한다.

### 4.2 정상 결과와 실패 결과만 유지

장소 결과 상태는 다음 두 종류만 사용한다.

```text
analyzed  정상 수집·분석·점수 계산 완료
failed    수집 또는 활성 분석을 완료하지 못함
```

`PlaceResultStatus.NOT_MATCHED`, `mismatchReason`과 관련 유효성 검사를 제거한다.
`RunStatus`의 `pending/running/completed/failed` 계약은 실행 전체 상태이므로 변경하지 않는다.

### 4.3 점수는 유일한 정렬 기준

정상 분석 장소는 점수가 낮거나 0점이어도 `analyzed`로 저장한다. 최종 점수는 기존 계산
규칙을 유지한다.

```text
finalScore = (photoScore × photoPercent + reviewScore × reviewPercent) / 100
```

- 가중치가 0인 분석은 계산에서 제외함
- 활성 분석 결과가 없으면 정상 결과를 만들지 않고 기존 오류 흐름으로 전달함
- 소수 첫째 자리에서 `ROUND_HALF_UP` 반올림함
- 동점 장소의 순서는 리포트 원본 순서를 유지하는 안정 정렬을 사용함

## 5. 데이터 흐름

```text
장소 상세 수집
  → 사진 분석: 점수 + 근거
  → 리뷰 분석: 점수 + 근거
  → 가중 최종 점수 계산
  → analyzed 결과 저장
  → 전체 analyzed 결과를 finalScore 내림차순으로 표시

수집·활성 분석·점수 계산 오류
  → failed 결과 저장
  → 실패 영역에 별도 표시
```

정상 분석 흐름에는 더 이상 점수 계산 전 분기나 기준 탈락 경로가 없다.

## 6. 백엔드 변경

### 6.1 분석 프롬프트와 출력

사진·리뷰 프롬프트에서 `전체적으로 충족할 때만 matched=true` 지시를 삭제한다. 대신
평가 기준과 실제 근거를 비교하여 0~10점 점수와 짧은 근거를 반환하도록 명시한다.

- 근거가 약하거나 상반되면 낮은 점수로 표현함
- 확인할 수 없는 특성은 임의로 충족 판정하지 않고 점수와 근거에 반영함
- 구조화 출력 스키마에는 점수와 근거만 포함함

### 6.2 점수 계산 서비스

`PlaceScoringService.calculate`의 mismatch 수집과 조기 반환을 제거한다. 활성 분석 결과의
존재를 검증한 뒤 항상 가중 최종 점수를 계산하여 `analyzed` 결과를 반환한다.

분석 결과가 누락된 경우의 `AnalysisInputError`는 유지한다. 이 오류는 상위 그래프의 기존
장소별 실패 처리에 의해 `failed` 결과로 변환된다.

### 6.3 그래프 집계와 리포트

- 그래프 로그에서 `matched`와 `not_matched` 집계를 제거함
- 완료 집계는 `analyzed`, `failed`만 기록함
- JSON 리포트의 정상 결과는 항상 `finalScore`를 포함함
- 실패 결과는 기존 `failureReason`을 유지함
- 리포트 결과 배열의 저장 순서는 변경하지 않으며 화면에서 정렬함

## 7. 실행 이벤트와 관측성

사진·리뷰 분석 완료 이벤트는 다음 공개 데이터만 제공한다.

```text
placeId
placeName
score
durationMs
```

사진 이벤트의 썸네일 URL, 입력 개수 등 기존 부가 필드는 유지한다. 단, `matched`는 SSE
이벤트 모델, 이벤트 생성 코드, 프런트 reducer에서 제거한다. 분석 근거는 기존처럼 장소
결과 이벤트와 최종 리포트에서 제공하며 진행 이벤트 계약을 새로 확장하지 않는다.

서버 진단 로그는 점수, 근거 요약, 소요시간, 성공·실패 상태를 계속 기록한다.
`matched`, `not_matched` 카운트는 기록하지 않는다. 기존 관측성 문서의 민감정보·사진 URL
제한은 그대로 적용한다.

## 8. 프런트엔드 동작

### 8.1 실시간 진행 화면

분석 이벤트에는 `N점`만 표시한다. `기준 충족`, `기준 미충족` 문구와 해당 조건부 렌더링을
삭제한다. 점수 근거, 사진 썸네일, 이벤트 스크롤 동작은 유지한다.

### 8.2 리포트 화면

- `analyzed` 결과 전체를 `finalScore` 내림차순으로 표시함
- 낮은 점수와 0점도 목록에서 제외하지 않음
- 정상 결과 목록 제목과 접근성 이름은 `평가 결과` 또는 `점수순 장소`로 변경함
- 통계의 `추천`은 `평가 완료`로 변경함
- `미충족` 통계와 `기준 미충족` 상세 영역을 제거함
- 정상 결과가 없을 때는 `평가 완료된 장소가 없음`으로 표시함
- `failed` 결과는 `확인 실패` 통계와 별도 상세 영역에 유지함

`추천`, `통과`, `충족`, `미충족`처럼 임계값이 있음을 암시하는 문구를 이번 기능 범위의
점수 결과 UI에서 사용하지 않는다.

## 9. 기존 리포트 처리

기존 `reports/`의 JSON 파일은 구현 시 모두 삭제한다. 기존 파일에는 `not_matched`와
`mismatchReason`이 포함될 수 있으므로 새 프런트 계약으로 읽거나 변환하지 않는다.

- `reports/` 디렉터리 구조와 이후 저장 위치는 유지함
- 실행 로그와 `artifacts/browser/` 자료는 삭제하지 않음
- 신규 실행부터 새 스키마의 리포트만 생성함
- 구버전 리포트 호환 코드는 추가하지 않음

## 10. 오류 처리

다음은 점수 부족이 아니라 실행 실패로 처리한다.

- 장소 상세 수집 실패
- 활성 사진 분석 결과 누락 또는 사진 분석 요청 실패
- 활성 리뷰 분석 결과 누락 또는 리뷰 분석 요청 실패
- 점수 계산 또는 결과 직렬화 실패

분석이 성공하여 0점이 생성된 경우는 실패가 아니다. `analyzed` 상태와 0점 최종 점수를
유지한다.

## 11. 테스트 전략

### 11.1 백엔드 단위 테스트

- `PhotoAnalysis`, `ReviewAnalysis`가 점수와 근거만으로 검증됨
- 분석 프롬프트와 구조화 출력에 `matched`가 없음
- 사진·리뷰 점수가 낮아도 가중 최종 점수가 계산됨
- 0점 결과가 `analyzed`로 생성됨
- 단일 활성 분석과 0% 가중치 계산이 기존 규칙대로 동작함
- 활성 분석 누락은 계속 `AnalysisInputError`가 됨
- `PlaceResult`가 `analyzed/failed` 상태 규칙만 허용함

### 11.2 그래프·API·이벤트 테스트

- 분석 완료 이벤트에 점수는 있고 `matched`는 없음
- 그래프 완료 집계에 `not_matched`가 없음
- report snapshot과 SSE 직렬화에 `mismatchReason`이 없음
- 장소별 실제 오류는 `failed`와 `failureReason`으로 유지됨

### 11.3 프런트엔드 테스트

- 정상 장소 전체가 최종 점수 내림차순으로 표시됨
- 낮은 점수와 0점 장소도 목록에 포함됨
- 동점 순서가 입력 순서를 유지함
- `기준 충족/미충족`, `추천`, `통과` 문구가 표시되지 않음
- 통계는 `평가 완료`, `확인 실패`만 표시함
- 실패 장소는 별도 영역에 표시됨
- 실시간 이벤트는 점수와 사진 썸네일을 계속 표시함

### 11.4 통합 검증

- Python 전체 테스트 실행
- 프런트엔드 테스트와 프로덕션 빌드 실행
- FastAPI와 프런트엔드를 각각 20003, 10003 포트에서 실행
- 웹에서 `신사역 / 일식 / 5개` 실행
- 정상 분석된 5개 장소가 점수순으로 리포트에 표시되는지 확인
- `기준 미충족` 분류나 문구가 생성되지 않는지 확인
- 실패 장소가 있을 경우 점수 부족이 아닌 실제 실패 사유인지 로그로 확인

## 12. 완료 조건

- 정상 분석된 모든 장소에 `finalScore`가 존재함
- 정상 분석된 모든 장소가 점수순 목록에 노출됨
- 백엔드와 프런트 계약에서 `matched`, `not_matched`, `mismatchReason`이 제거됨
- 점수 결과 UI에서 이진 충족·추천 표현이 제거됨
- 실제 실패만 `failed`로 분리됨
- 기존 JSON 리포트가 삭제되고 신규 스키마 리포트만 남음
- 자동 테스트, 빌드, `신사역 / 일식 / 5개` 실사용 검증이 통과함
